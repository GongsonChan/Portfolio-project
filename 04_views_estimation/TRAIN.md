# 04_views_estimation - 모델 학습 설계

피처/타겟 준비(`FEATURE_DESIGN.md`)는 끝난 상태. 여기는 그 다음 단계인 "학습 → 스태킹 → 추론" 설계.

## 전체 단계
1. **Walk-forward 폴드 나누기** — 시간순으로 "과거로 학습 → 그 다음 구간 예측" 폴드 분할. 타겟이 21거래일짜리라 학습구간/검증구간 사이에 21일 embargo(여유구간) 필요 (안 그러면 라벨이 검증구간까지 침범해서 미세한 미래정보 누출 생김)
2. **베이스모델 학습**:
   - 팩터 기반(5개): LightGBM, RandomForest, Ridge, Lasso, **HuberRegressor**(이상치에 강한 robust 선형회귀 — Ridge/Lasso의 제곱손실과 다른 손실함수. 소구간 테스트 corr=0.062로 양호, 1.8초로 거의 공짜라서 채택) — 라쏘/릿지는 둘 다 선형이지만 라쏘의 L1이 상관관계 높은 피처(mom_1m/3m/6m 등)를 자동으로 0으로 눌러 걸러내는 효과가 릿지와 달라서 유지
   - **RandomForest 하이퍼파라미터 재조정**: 전체 25폴드 OOF 돌려보니 RandomForest가 5개 모델 중 꼴찌(corr=0.011, 나머지는 0.025~0.059)로 나와서 underfitting 의심 → fold1(진짜 embargo 구조, train 38만행)에서 `max_depth`/`min_samples_leaf` 스윕한 결과 `max_depth=8, leaf=50`(기존) corr=0.096 vs `max_depth=None, leaf=100` corr=0.121로 27% 개선 — 100만행+ 데이터엔 깊이를 고정 캡 씌우는 것보다 리프 크기로만 규제하는 게 더 잘 맞음. 레지스트리에 반영 완료, **전체 팩터 OOF 재실행 필요**
   - LightGBM도 같은 fold1 기준으로 `num_leaves`/`n_estimators`/`learning_rate` 스윕해봤는데, **지금 설정(leaves=31)이 제일 좋았음**(corr=0.115, 더 키우면 0.087~0.110으로 오히려 하락) — leaf-wise 성장이라 depth-wise인 RandomForest와 달리 이미 용량을 효율적으로 쓰고 있었던 것. 변경 없음
   - **신경망(MLP, MLP-deep, TabNet)과 KNeighborsRegressor는 시도했다가 전부 제외**: MLP 하이퍼파라미터 6종 스윕(은닉층 크기 16~128, alpha 1e-5~1e-1, early_stopping on/off)과 KNN 5종 스윕(k=10~500, uniform/distance)을 돌려봤는데 **둘 다 전부 OOF 상관계수가 음수**로 나옴 (KNN은 k가 커질수록 더 나빠짐) — 튜닝 문제가 아니라 이 피처셋/타겟 조합엔 신경망/국소평균 방식이 트리·선형모델 이상으로 뽑아낼 신호가 없다는 뜻 (tabular 데이터에서 트리모델이 딥러닝보다 보통 더 잘한다는 일반적 결과와도 일치, Grinsztajn et al. 2022; KNN은 31차원에서 차원의 저주 영향도 있을 수 있음). TabNet은 MLP 결과 나온 뒤엔 정확도 측정도 안 하고 제외 (CPU 371초/GPU 388초로 비싼데 같은 신경망 계열이라 같은 결과 나올 게 뻔해서 측정 비용도 아낌)
   - 다음 후보(아직 안 씀): **XGBoost**(LightGBM과 같은 boosting 계열이라 다양성 기여는 제한적이지만 거의 공짜), **ExtraTrees**(RandomForest보다 더 무작위화된 bagging)
   - 시퀀스 기반(3개, `sequence.py`의 초과수익률 시퀀스 입력, **윈도우 252거래일(~1년)**): GRU, 1D-CNN, **PatchTST**(시계열 전용 Transformer 변형, 시퀀스를 패치 단위로 쪼개서 봄) — 서로 다른 계열(순환/합성곱/어텐션)로 골라서 다양성 극대화. LSTM 대신 GRU 택1 (같은 게이트형 RNN 계열이라 다양성 기여 적음). Informer/Autoformer 같은 초장기·강계절성 특화 변형은 저희 시퀀스 길이(252)엔 과함 — PatchTST가 구현 부담 대비 가장 현실적
     - **윈도우를 60일에서 252일로 변경한 이유**: 원래 60일은 임의로 잡은 값이었는데, 팩터모델이 이미 12-1개월 모멘텀(252일 윈도우)을 핵심 피처로 쓰고 있어서, 시퀀스모델도 그 정도 과거는 봐야 비슷한 장기 패턴을 스스로 발견할 기회가 생김. 10년치 데이터가 있어 굳이 짧게 자를 이유도 없고, GRU/CNN/PatchTST 전부 252스텝 정도는 계산 부담 없음 (Transformer 어텐션 계산량도 252²로 여전히 작음). `MIN_HISTORY_DAYS=273`(종목 자격조건)이랑도 이미 들어맞아서 추가 제약 없음
3. **OOF 예측 생성** — 각 폴드에서 "그 폴드 학습엔 안 쓰인" 구간에 대해 베이스모델들이 예측값 생성, 전체 기간에 대해 누적
4. **메타모델 학습** — OOF 예측들을 입력으로, 실제 타겟을 라벨로 메타모델 학습 → 베이스모델들을 어떻게 섞을지 배움. 후보는 **Ridge**(선형, 기본/안전) vs **LightGBM**(얕은 트리, 비선형이지만 저차원 입력에 안정적) 둘 다 시도해서 OOF 검증 성능 더 좋은 쪽 채택 — MLP나 "최신 tabular 모델"은 메타모델 입력이 겨우 8개 숫자(베이스모델 예측값)뿐이라 과한 용량 대비 과적합 위험만 커서 제외 (베이스모델 레벨에서나 그런 복잡한 모델이 의미 있음)
5. **실전용 모델 재학습** — 베이스모델들을 전체 데이터로 한 번 더 학습 (OOF 때는 일부러 최신 구간을 검증용으로 비워뒀으니, 실전 배포 직전엔 그 구간까지 다 포함해서 재학습)
6. **모델 저장** — 학습된 모델 객체는 파일(pickle/joblib 등)로 디스크 저장, "언제 학습됐는지/성능이 어땠는지" 메타데이터만 DB에 기록해서 "최신 모델이 뭔지" 조회 가능하게
7. **일일 추론 스크립트** — 저장된 최신 모델 불러와서, 그날 유니버스(02_filter 결과)에 대해 Q 예측, `views` 테이블 등에 저장 (`label` 시스템 재사용 — 기본값 vs 커스텀 분리)
8. **Ω(불확실성) 산출** — ~~베이스모델들 간 예측 불일치(분산)~~는 재고함: 모델들이 서로 의견이 갈리는 정도는 "이 예측이 실제로 얼마나 틀릴지"랑 다른 개념 (8개 모델이 전부 똑같이 틀릴 수도 있음 — 그럼 불일치는 0인데 불확실성은 커야 맞음). 대신 **`Var(실제 target - 메타모델 예측값)`을 티커별로, 최근 1년치 OOF 데이터 기준**으로 계산해서 Ω로 사용 — "이 종목에 대한 예측이 실제로 얼마나 못 믿을만했는지"를 직접 재는 거라 Omega 개념에 더 맞음. `update_all_oof.py`로 OOF가 매주 계속 쌓이는 구조 덕분에 이게 가능해짐. (티커당 1년에 최대 ~52개 샘플이라 노이즈 있을 수 있음 — 실제 구현 시 고려)
 
## 핵심 설계 결정
- **풀링(pooling)**: 02_filter가 뽑은 유니버스가 아니라 **전체 적격 종목**으로 학습 (03_sigma_estimation의 GARCH랑 같은 패턴 — "학습은 넓고 싸게, 추론만 유니버스로 좁힘"). 샘플 수가 28배 차이 나고(4.6만 vs 131만 행), 필터 기준이 연속적 점수라 전체 풀에도 "필터 통과할만한" 사례가 이미 충분히 섞여있어서 노이즈 걱정보다 데이터 부족 걱정이 더 큼.
- **시간 기준 CV 필수**: 랜덤 k-fold 절대 금지 (look-ahead bias). walk-forward + embargo만 사용.
- **베이스모델 다양성**: 피처 기반 모델(트리/선형/신경망) + 시퀀스 기반 모델(RNN/CNN/Attention) 혼합 — 같은 (종목,날짜) 타겟을 서로 다른 입력 표현·서로 다른 메커니즘으로 보게 해서 스태킹 효과 극대화.
- **모델 추가/제거가 쉬운 구조(레지스트리 패턴)**: 모든 베이스모델은 겉보기엔 `fit(X, y)` / `predict(X)`만 가진 동일한 인터페이스로 통일 (sklearn 계열은 원래 이 형태, 딥러닝 모델은 학습루프를 감싼 래퍼 클래스로 맞춤). 실제 모델 목록은 코드 한 군데(딕셔너리)에서만 관리:
  ```python
  FACTOR_MODELS = {"lightgbm": ..., "random_forest": ..., "ridge": ..., "lasso": ..., "huber": ...}
  SEQUENCE_MODELS = {"gru": ..., "cnn": ..., "patchtst": ...}
  META_MODELS = {"ridge": ..., "lightgbm_leaves7": ..., "lightgbm_leaves15": ..., "lightgbm_leaves31": ...}  # LightGBM은 num_leaves 3종 비교, 전부 시도해서 OOF 성능 더 좋은 쪽 채택
  ```
  Walk-forward/OOF 루프는 이 딕셔너리를 순회만 하므로, 모델 추가/제거 시 이 목록에 한 줄만 추가/삭제하면 되고 OOF/스태킹 핵심 로직은 안 건드림.

### 메모: 웹 어드민 패널에서 모델 on/off (향후)
나중에 웹에서 사용자(관리자)가 "이번 학습엔 어떤 베이스모델 쓸지" 체크박스로 끄고 켤 수 있게 할 예정. 레지스트리 패턴 덕분에 이미 거의 준비됨 — 학습 함수는 처음부터 "항상 레지스트리 전체"가 아니라 **"쓸 모델 이름 리스트를 인자로 받고, 안 주면 기본값(전체)"** 형태로 설계해둘 것. 그러면 나중엔 체크된 모델 이름들만 리스트로 넘기면 끝. 02_filter의 가중치 커스터마이징(`weights` 파라미터), `label` 시스템(기본값 vs 사용자 커스텀 분리)이랑 동일한 패턴으로 통일.

## 진행 순서 제안
한 번에 1~8번 다 구현하면 디버깅이 어려우니:
1. **1단계로 LightGBM 하나만(레지스트리엔 처음부터 넣어두되 1개만)** "폴드 나누기 → 학습 → OOF 예측"까지 먼저 끝까지 뚫어서 전체 파이프라인 검증
2. 그 다음 RandomForest, Ridge, Lasso, MLP를 레지스트리에 하나씩 추가해서 스태킹(4~5번) 완성 — 메타모델은 Ridge/LightGBM 둘 다 학습해서 비교 (TabNet은 시도 후 제외, 위 참고)
3. 마지막에 시퀀스 모델(GRU → CNN → PatchTST 순으로 하나씩) 추가해서 베이스모델 다양성 확보
4. 6~8번(저장/추론/Ω)은 전체 스태킹 구조 완성 후 진행

## 향후 개선사항
- **시퀀스 OOF 업데이트가 매번 비쌈**: `update_sequence_oof.py`가 돌 때마다 `build_sequence_training_set()`이 전체 역사(462일)를 가격데이터부터 다시 계산함 (날짜당 ~12.7초 × 462일 ≈ 98분). 팩터 쪽은 `ml_features`에 미리 계산해서 저장해두니까 테이블 한 번 읽으면 끝(~9분)인데, 시퀀스는 그런 캐싱이 없어서 매주 똑같은 98분을 반복 지불함. "주말에 한 번 도는 거니까 괜찮다"로 일단 넘기지만, 나중엔 시퀀스도 `ml_features`처럼 DB에 캐싱해서 새로 생긴 날짜만 계산하는 구조로 바꾸는 게 맞음.
