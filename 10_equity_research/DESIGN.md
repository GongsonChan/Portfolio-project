# 10_equity_research 설계 (핵심 기능 구현 완료 — 남은 건 daily_update.py 편입뿐)

## 목표
06의 최종 추천 포트폴리오 종목들에 대해 DART 공시 + 뉴스를 활용해 LLM 기반 기업분석 보고서를 자동 생성하고, 텍스트 분석 기반 기업간 유사도를 그래프로 보여준다.

## 왜 필요한가
- 지금까지 파이프라인은 "몇 % 비중"이라는 숫자로 끝남 — "왜 이 종목인가"를 설명하는 서사가 없음. 리포트 수준으로 확장하면 실제 애널리스트가 읽는 결과물에 가까워짐.
- 09_risk_management가 수익률 상관관계 기준 집중도(컴포넌트 VaR)를 보여줬다면, 이건 **사업모델 기준 유사도/집중도**를 보여주는 보완적 관점 — "수익률은 안 겹치는데 사업은 겹치는" 케이스를 잡아낼 수 있음.
- **09가 정량적 리스크(VaR/ES, 숫자)를 다뤘다면, 10은 정성적 리스크(뉴스/공시 기반 서술형 평가)를 다룸** — 둘이 서로 다른 축에서 "이 종목이 위험한가"에 답하는 짝. VaR는 과거 수익률 분포로만 리스크를 추정하는데, 소송/규제/경영진 리스크 같은 건 과거 가격 움직임엔 아직 안 드러났을 수 있어서 뉴스·공시 기반 정성 평가가 그 공백을 메워줌.

## 계산 대상
06_post_filter.final_portfolio의 종목들 (09와 동일 패턴 — 05의 유니버스 전체가 아니라 실제로 "보유하게 될" 최종 선별 포트폴리오 기준).

## 범위 — 2단계로 나눔

### 1단계: DART + 뉴스 기반 기업분석 보고서 (LLM)
- **데이터 소스**:
  - DART(OpenDART API) — 사업보고서/분기보고서 등 공시 자료. 키 발급 완료(`01_data_load/.env`의 `DART_API_KEY`).
  - 뉴스 — **네이버 검색 API로 확정**. 키 발급 완료(`NAVER_CLIENT_ID`/`NAVER_CLIENT_SECRET`, 둘 다 헤더로 같이 보내야 함).
- **LLM**: 06_post_filter에서 이미 쓰는 Anthropic API 재사용 (`.env`의 `ANTHROPIC_API_KEY`) — 새 크레덴셜 작업 불필요.
- **산출물**: 종목별 보고서, 08_web에서 **각각 독립된 칸**으로 보여줄 네 부분으로 구성(사용자 피드백으로 재설계 — 처음엔 "사업의 내용" 원문을 그냥 그대로 보여줬는데, 그건 리포트가 아니라 복붙이라는 지적을 받고 전면 재작업함):
  1. **기업개요 (요약)** — DART 사업보고서("사업의 내용") 원문을 LLM이 **5문장 이내로 새로 정리**한 요약 (원문 복붙 아님). 주요 사업부문, 핵심 제품/거래처 등.
  2. **재무제표** — DART의 **별도 재무제표 API**(`fnlttSinglAcntAll.json`)에서 가져온 실제 수치(매출액/영업이익/당기순이익/자산총계/부채총계/자본총계/영업활동현금흐름, 당기·전기 비교) 표 + 그 숫자에 **근거한** 3문장 이내 LLM 요약. 사업보고서 텍스트에서 숫자를 뽑는 게 아니라 DART의 구조화된 재무제표 엔드포인트를 따로 호출 — 훨씬 정확하고 안정적.
  3. **최신 동향** — 집중 중인 사업/투자 분야, 주요 거래처·계약·수주 현황 등을 사업보고서 원문 기준으로 LLM이 정리 (외부 뉴스가 아니라 공시 자체 기준).
  4. **뉴스 요약 + 정성적 위험도 평가** — 사업/공시/뉴스를 종합해서 LLM이 평가. 06_post_filter의 섹터 분류처럼 **구조화 출력(Pydantic 스키마)**로 등급(예: 낮음/중간/높음)과 그 근거 서술을 같이 뽑아내는 방식 — 등급만 있으면 왜 그런지 추적이 안 되고, 서술만 있으면 한눈에 비교가 안 되니 둘 다 필요.
- **생성 주기: 매일, 단 통째로 재생성하지 않음 — 03/04의 "fit/update 분리" 원칙 재사용**:
  - **뉴스 요약 + 정성적 위험도 평가**: 매일 재생성 (뉴스는 매일 바뀌는 게 핵심이라 이 부분이야말로 매일 돌려야 의미 있음). 전체 리포트 중 유일하게 진짜 "데일리"인 부분.
  - **사업 개요 + 실적 요약(DART 기반)**: DART 공시는 분기 단위로만 바뀌니 매일 다시 LLM에 넣어 요약하는 건 낭비 — 새 공시가 감지됐을 때만(또는 최대 주 1회 체크) 재생성, 그 외엔 캐시된 걸 그대로 씀.
  - 06의 `final_portfolio`가 매일 바뀔 수 있으니: **신규 편입 종목**은 전체(사업개요+실적+뉴스+위험도) 새로 생성, **계속 보유 종목**은 뉴스/위험도만 갱신, **제외된 종목**은 생성 안 함(비용 절감).

### 2단계: 텍스트 기반 기업 유사도 그래프
- DART 사업보고서 텍스트(사업의 내용 등)를 임베딩해서 종목 간 코사인 유사도 계산.
- **임베딩 모델: `jhgan/ko-sroberta-multitask` (로컬, `sentence-transformers`)로 확정.** 한국어 의미 유사도 태스크 특화 모델이라 DART 사업보고서 같은 한국어 비즈니스 텍스트에 범용 다국어 모델보다 적합, API 키 불필요(이미 KRX/Anthropic/DART/네이버 4개 키 관리 중이라 더 안 늘림), 종목 수(8~10개) 규모면 로컬 추론으로 충분. 새 의존성은 `sentence-transformers`/`torch` 추가뿐(04가 이미 PyTorch류를 쓰고 있어 생태계상 크게 낯선 추가는 아님).
- 그래프로 시각화 (08_web에 페이지 추가, 또는 별도 아티팩트).
- 09의 컴포넌트 VaR(수익률 상관관계 기준)와 나란히 비교하는 게 목적 — 서로 다른 두 축(수익률 vs 사업모델)에서의 집중도를 교차 검증.

## 구현 메모

### DART 연동
- `src/dart_client.py` — corpCode.xml(ZIP) 다운로드+파싱, company.json(기업개요), list.json(정기공시 목록) 래퍼. KRX 클라이언트와 같은 재시도 패턴.
- `db/dart_tables.sql` — `dart_corp_codes`(티커↔corp_code 매핑, 119,977건 — DART는 비상장 법인까지 다 포함해서 그중 KRX 상장은 4,013개뿐), `dart_company_overview`(종목별 기본정보 캐시).
- `scripts/update_corp_codes.py` — corp_code 마스터 리스트 1회성 동기화(자주 안 바뀌니 daily_update.py엔 안 넣음).
- `scripts/fetch_company_overview.py` — 06 최종 포트폴리오 종목들의 DART 기본정보(대표이사/설립일/업종코드) 조회+캐싱. 10종목 전부 테스트 성공.
- `src/filing_parser.py` + `scripts/fetch_business_description.py` — "사업의 내용" 원문 추출. `document.xml` API로 사업보고서 전체(ZIP, 삼성전자 기준 8.2MB)를 받아서 로마숫자 챕터 제목("II. 사업의 내용")을 찾아 다음 로마숫자 챕터 전까지의 텍스트를 모음. 2단계(임베딩 유사도)와 **LLM 리포트(아래)의 원재료** — 직접 사용자에게 보여주는 게 아니라 LLM이 읽고 재정리하는 입력으로만 씀. `dart_business_description` 테이블에 캐싱(DART 연동과 같은 이유로 매일 안 돌림). **10종목 전부 테스트 성공** (아래 "알려진 버그/교훈" — 처음엔 0/10이었다가 세 가지 실제 문제를 하나씩 찾아 고침).
- `find_latest_annual_report(corp_code)` — "최신 정정 아닌 사업보고서 찾기" 로직을 `dart_client.py`에 공용 헬퍼로 분리 (`fetch_business_description.py`/`generate_equity_report.py` 둘 다 재사용, 로직 중복 방지).
- `src/financial_statements.py` + DART `fnlttSinglAcntAll.json`(`fetch_financial_statements`) — **재무제표는 사업보고서 텍스트에서 숫자를 파싱하는 게 아니라, DART의 별도 구조화 API에서 직접 가져옴.** IFRS 표준 계정 태그(`account_id`)로 매칭해서 매출액/영업이익/당기순이익/자산총계/부채총계/자본총계/영업활동현금흐름 7개 핵심 지표(당기+전기)를 추출. **업종별로 손익계산서 섹션(`sj_div`)과 계정 태그가 다름을 실제 데이터로 발견**(제조업은 `IS`+`dart_OperatingIncomeLoss`, 금융지주는 `IS` 섹션 자체가 없고 `CIS`+`ifrs-full_ProfitLossFromOperatingActivities`, 매출액은 아예 없음) — 아래 "알려진 버그/교훈" 참고, `KEY_ITEMS`가 섹션 후보 리스트 + 계정태그 후보 리스트를 둘 다 순서대로 시도하도록 설계됨. CFS(연결)가 없으면(자회사 없는 회사) OFS(개별)로 폴백.
- `src/report_writer.py` + `scripts/generate_equity_report.py` — 사업보고서 발췌 텍스트 + 재무제표 핵심 수치를 LLM에 같이 줘서 **기업개요/최신동향/재무요약 3개를 한 번의 배치 호출로 생성** (06/뉴스평가와 같은 배치 패턴). `db/equity_report_tables.sql`(`equity_report`)에 저장.
- **요약 길이 확장(8문장/5문장) — "~문장 이내"는 상한일 뿐 실제로 안 늘어남**: 처음엔 overview_summary 5→8문장, financial_summary 3→5문장으로 숫자만 올렸는데, 재생성해보니 **길이가 거의 그대로**(4문장 안팎)였음 — "이내로"라는 표현이 "최대 이만큼 써도 된다"는 상한선일 뿐이라 LLM이 그냥 짧게 쓰고 끝내버림. "~문장**으로** 작성해라" + **반드시 언급할 항목 체크리스트**(사업부문/제품/거래처/생산거점/원재료/경쟁환경/신사업/종속기업 8개, 발췌문에 있는 것만)로 바꾸니 실제로 2배 이상 길어짐(232자→596자, 체크리스트 항목이 실제로 다 채워짐). 동시에 `business_text` 슬라이스도 4000자→8000자(저장된 전체)로 늘려서 LLM이 쓸 원재료를 더 줌. 이 과정에서 `max_tokens=8192`가 다시 모자라서 JSON이 또 잘림(같은 종류의 버그 재발 — 이번엔 "회사 수가 많아서"가 아니라 "종목당 출력이 길어져서") → `16384`로 상향.
- **문단 분리 — 2번의 시도 끝에 "필드 이름"으로 해결**: 8문장을 한 덩어리 `<p>`로 렌더링하니 가독성이 떨어진다는 지적(스크린샷)으로 체크리스트 그룹별 문단 분리를 시도. (1) 프롬프트에 "문단은 줄바꿈 두 번(\n\n)으로 구분해라"만 추가 → **완전히 무시됨** (DB에 저장된 텍스트에 `\n` 0개, 실측 확인). (2) `overview_summary: list[str]`로 스키마를 바꾸고 "정확히 3개의 배열 원소로"라고 지시 → 모델이 "배열 = 문장 단위"로 해석해서 **문단 3개가 아니라 문장 7개**가 나옴(배열 슬롯 자체엔 "이게 문단이다"라는 의미가 없어서). (3) 최종: `overview_who`/`overview_how`/`overview_position`(그리고 `financial_income`/`financial_position`)처럼 **의미를 담은 필드 이름**으로 쪼개서 LLM이 채우게 하고, Python에서 `_join_paragraphs()`로 `\n\n` join해서 기존 TEXT 컬럼(`overview_summary`/`financial_summary`)에 저장 — 10종목 전부 3개/2개 문단으로 안정적으로 분리됨(실측). 08_web 쪽은 `templates.env.filters["paragraphs"]`(app.py, `\n\n` split)로 받아서 문단마다 별도 `<p>` 렌더링.

### 네이버 뉴스 + LLM 평가
- `src/naver_client.py` — 뉴스 검색 래퍼, HTML 태그/엔티티 정리.
- `src/news_assessment.py` — 06의 섹터 분류와 같은 패턴(Claude Haiku, Pydantic 구조화 출력)으로 **뉴스 요약+핵심 이슈+정성적 위험도를 한 번의 LLM 호출로 전체 포트폴리오 배치 처리**(종목마다 따로 호출하지 않음, 06의 배치 분류와 같은 비용 절감 이유). `assess_via_llm()`(단발 호출)과 `assess_with_consistency()`(다수결 래퍼, 아래 참고) 둘 다 제공.
- `db/news_tables.sql` — `equity_news_assessment`(as_of_date/label/ticker 기준, 뉴스 요약+이슈+위험도등급+근거+`n_runs`/`n_agree`를 한 테이블에), `equity_news_articles`(원본 기사 title/link/pub_date, rank 순 — 사용자가 "LLM 요약만 있고 실제 참고한 뉴스 원문이 안 보인다"고 지적해서 추가. 08_web에서 뉴스 요약 패널 아래에 제목(링크)+발행일 목록으로 노출).
- `scripts/update_news_assessment.py` — 매일 재생성될 부분(DESIGN.md "생성 주기" 참고). 아직 `daily_update.py`엔 미편입(모듈 전체 완성 후 한 번에 연결 예정).
- **다수결(self-consistency) + 프롬프트 기준 명시로 재현성 개선**: 아래 "알려진 버그/교훈"에서 찾은 등급 불안정 문제(10종목 중 5개가 낮음/중간 사이 흔들림)를, (1) 프롬프트에 낮음/중간/높음 각각의 구체적 판단 기준을 명시하고 (2) `assess_with_consistency(companies, n_runs=5)`로 같은 입력을 5번 돌려 다수결 + 일치율(`n_agree`/`n_runs`)을 저장하는 방식으로 개선. 재검증 결과 **10종목 중 9개가 5/5 만장일치**, 나머지 1개(475150)만 4/5로 — 기준 명시만으로도 대부분의 흔들림이 해소됐고, 남은 미세한 불확실성은 숨기지 않고 `n_agree` 숫자로 그대로 노출.
- **"참고한 뉴스" 원문 링크 목록 추가**: 사용자 피드백("LLM 요약만 있고 실제 근거 뉴스가 안 보인다")으로 `equity_news_articles` 테이블(제목/링크/발행일, rank순) 신설 — 매일 가져온 뉴스를 LLM에 넘기기 전에 그대로 저장해서, 08_web 뉴스 패널 아래에 실제 기사 링크 목록(제목 클릭 가능, 발행일 표시)을 보여줌.
- **기업명이 스포츠 구단 이름과 겹치는 문제 발견/완화 (사용자가 웹에서 직접 발견)**: 삼성화재(V리그 배구단 "삼성화재 블루밍스" + "삼성화재배" 바둑대회)와 현대모비스(KBL 농구단 "현대모비스 피버스")는 전부 동명의 스포츠 구단이 있어서, 회사명으로 네이버 뉴스를 검색하면 경기 결과/순위 기사가 대거 섞여 들어옴 — 처음엔 뉴스 요약 자체가 "배구 경기 얘기"로 나왔음. **쿼리를 바꾸는 시도는 실패**("삼성화재 주가"처럼 한정어를 붙이면 그 종목은 깨끗해지지만, 다른 종목(신한지주/기아 등)은 오히려 전체 증시 동향 뉴스로 희석돼 더 나빠짐 — Naver 검색이 진짜 AND 검색이 아니라서) → **키워드 기반 사후 필터**(`filter_relevant_articles`)로 전환, 30건을 넉넉히 받아서 거른 뒤 상위 10건만 사용. 처음엔 "배구"/"감독" 같은 뻔한 단어만 걸렀는데 "7:13→28:26", "33득점 폭발", "[사진] 또 졌다" 같은 종목 전문용어/스코어 패턴이 더 많이 새어 들어와서, **실제 관측된 기사 제목을 보고 키워드를 계속 보강**(끝없는 두더지잡기라는 걸 인지하고 있음 — 블랙리스트 기반 필터는 완벽할 수 없는 휴리스틱으로 문서화). 2차 안전장치: 필터링 후에도 남은 노이즈가 있을 경우, **LLM 자체가 "이건 스포츠 얘기였다"고 정직하게 보고**하는 걸 확인(현대모비스 테스트 중 "사업 관련 핵심 이슈는 없으며, 프로농구 팀 성적 부진이 주요 기사 내용"이라고 명시) — 필터가 완벽하지 않아도 LLM이 가짜 비즈니스 내러티브를 지어내진 않는다는 걸 실제로 검증함. 필터링 후 기사가 0건이면("현대모비스"는 한 차례 30건 전부 걸러짐) 프롬프트 지침대로 "최근 특이 뉴스 없음"으로 정직하게 처리.

### 알려진 버그/교훈
- **NAVER API HUB ≠ NAVER Developers**: 발급받은 네이버 키가 401로 계속 거부돼서 조사해보니, 사용자가 키를 받은 곳이 옛날 개발자센터(`developers.naver.com`, `X-Naver-Client-Id`/`X-Naver-Client-Secret` 헤더, `openapi.naver.com` 엔드포인트)가 아니라 **NCP의 NAVER API HUB**(`X-NCP-APIGW-API-KEY-ID`/`X-NCP-APIGW-API-KEY` 헤더, `naverapihub.apigw.ntruss.com` 엔드포인트)였음 — 같은 키 쌍인데 완전히 다른 제품/인증 스킴이라 생긴 문제. curl로 두 엔드포인트를 직접 비교해서 원인을 확정한 후 수정.
- **구조화 출력 JSON 중간 절단**: `max_tokens=4096`이 10종목 배치 응답엔 가끔 모자라서 JSON이 중간에 끊겨 `pydantic.ValidationError`가 간헐적으로 남 → `8192`로 상향.
- **ticker 필드 오염**: LLM이 가끔 `ticker` 필드에 `"000270 기아"`처럼 종목명을 같이 써서 결과 매칭(dict key)이 깨짐 → 프롬프트에 명시적으로 금지 + Pydantic `field_validator`로 공백 기준 첫 토큰만 추출하도록 방어.
- **정성적 위험도 등급의 run-to-run 불안정성 (개선 완료)**: `scripts/check_assessment_consistency.py`로 **같은 뉴스 입력**에 대해 `assess_via_llm`을 5번 반복 호출해본 결과, 10종목 중 5개가 낮음/중간 사이에서 등급이 흔들림(예: 475150은 낮음 3회·중간 2회). 1차 시도(`temperature=0`)는 **`claude-haiku-5-5`가 temperature 파라미터 자체를 더 이상 지원하지 않아**(API가 `` `temperature` is deprecated for this model ``으로 거부) 막다른 길이었음 — 신형 Claude 모델이 샘플링 온도 제어를 아예 노출하지 않는다는 걸 이번에 처음 확인. 대신 (a) 프롬프트에 등급별 구체적 판단 기준 명시 + (b) 다수결(`assess_with_consistency`)을 **같이 적용**해서 개선 — 재테스트 결과 9/10 종목이 5/5 만장일치로 안정화됨 (위 "네이버 뉴스 + LLM 평가" 참고).
- **DART `document.xml`이 well-formed XML이 아님 (처음엔 0/10 실패)**: 사업보고서 원문을 받아서 파싱하는데 10종목 전부 실패. 실제로 하나씩 받아서 디버깅한 결과 세 가지 문제가 겹쳐 있었음:
  1. 본문 파일을 `zf.namelist()[0]`으로 집었는데, ZIP 안엔 본문 외에 감사보고서/연결감사보고서 등 첨부파일도 같이 들어있어서(삼성전자 기준 3개 파일) 파일 순서에 기대면 안 됨 → 파일명이 정확히 `{rcept_no}.xml`인 것만 명시적으로 선택하도록 수정.
  2. 본문 안에 이스케이프 안 된 `&`가 그대로 있음(예: "R&D") — HWP→XML 변환 과정의 흔한 문제.
  3. `< TV 사업부문 >`, `<ACI 코리아>`처럼 원본 한글 문서의 장식용 꺾쇠가 깨진 XML 태그로 읽힘 — 문자로 시작하는 패턴까지 나와서 정규식으로 하나하나 막는 게 한계에 부딪힘.
  2번/3번은 정규식으로 땜질하다가, 같은 종류의 실제 깨진 마크업이 계속 새로 나오는 걸 보고 **`lxml`의 관대한 복구 파서(`XMLParser(recover=True)`)로 전면 교체**함 — "진짜 세상의 깨진 XML을 파싱하는" 표준 도구를 쓰는 쪽으로 방향을 바꾼 것. 추가로 "[첨부정정]사업보고서"(첨부파일만 고친 정정 공시)가 원본보다 날짜가 늦어서 더 최근 걸로 잘못 선택되는 문제도 발견 — `report_nm`이 "사업보고서"로 **시작하는** 것만 고르도록(=정정 공시 제외) 필터 수정. 세 가지 다 고친 뒤 **10/10 전부 성공**.
- **LLM이 "thinking"에 출력 토큰을 다 써버려서 구조화 출력이 통째로 None (리포트 LLM 호출)**: 10종목 배치(사업보고서 발췌+재무제표, 프롬프트 4만자)를 한 번에 처리하려니 `claude-haiku-5-5`가 `max_tokens=8192` 중 5,465토큰을 내부 "thinking"에 써버리고 `stop_reason="max_tokens"`로 끊겨서 `response.parsed_output`이 `None`으로 나옴 (바로 전에 봤던 "JSON 중간 절단"과는 다른 원인 — 이번엔 입력 자체가 큰 배치 호출이라 발생). 요약 작업이라 깊은 추론이 필요 없다고 판단해 `thinking={"type": "disabled"}`로 꺼서 해결 — 추가로 `parsed_output is None`일 때 `stop_reason`을 담아 명시적으로 raise하도록 방어 코드도 추가(향후 같은 증상이면 바로 원인을 알 수 있게).
- **Postgres `NUMERIC` → Python `Decimal`, 템플릿에서 float 나눗셈 실패**: 재무제표 수치를 억원 단위로 변환하려고 `row.current / 1e8`을 Jinja에서 했더니 `Decimal`과 `float` 연산이 안 돼서 `TypeError` — 08_web의 `_build_financial_rows()`에서 미리 `float()`로 캐스팅한 뒤 템플릿에 넘기도록 수정 (Jinja에서 DB NUMERIC 값을 바로 산술 연산하지 말 것).
- **금융지주회사는 재무제표 계정 체계 자체가 다름 (사용자가 웹에서 직접 발견)**: 신한지주(055550)에서 매출액/영업이익/당기순이익이 전부 "-"로 나왔는데, 재무제표 텍스트 밑 LLM 요약엔 숫자(4조 9,716억)가 적혀 있어서 둘이 안 맞는 걸 사용자가 지적. 원인 두 가지가 겹쳐 있었음:
  1. **추출 로직 버그**: 제조업(삼성전자)은 손익계산서가 `IS` 섹션에 있는데, 금융지주는 `IS` 섹션이 아예 없고 전부 `CIS`(포괄손익계산서)에만 있음 — `sj_div="IS"`로만 찾던 코드가 전혀 못 찾음. 영업이익 계정 태그도 업종별로 다름(제조업 `dart_OperatingIncomeLoss` vs 금융업 `ifrs-full_ProfitLossFromOperatingActivities`) → `KEY_ITEMS`를 **섹션 후보 리스트 + 계정태그 후보 리스트**로 재설계해서 해결. 재검증 결과 영업이익 7조 234억/순이익 5조 845억으로 정확히 잡힘.
  2. **매출액은 실제로 없는 게 맞음**: 은행/지주사는 이자수익/수수료수익/보험수익으로 나눠 보고하지 단일 "매출액"이 없음 — 이건 버그가 아니라 업종 특성이라 억지로 합산하지 않고 "-"로 그대로 둠.
  3. **LLM이 "데이터 없음" 항목을 사업보고서 원문에서 끌어다 메꾸려 한 것(더 심각한 문제)**: 표엔 "-"인데 LLM 요약엔 DART 실수치(5.08조)와도 다른 엉뚱한 숫자(4.97조)가 적혀있었음 — 재무제표에 없는 값을 다른 곳(사업보고서 텍스트)에서 가져다 쓴 것으로 보임. 프롬프트에 "데이터 없음인 항목은 언급하지 말고 건너뛰어라, 사업보고서 발췌문에서도 숫자를 가져오지 마라"를 명시해서 해결 — 재검증 결과 "매출액은 데이터가 없어 언급하지 않는다"로 정직하게 처리됨.
