# 03_sigma_estimation 설계

## 목표
BL 모델에 넣을 공분산행렬(Σ)을 DCC-GARCH로 추정한다. 코드 세부사항은 각 파일의 docstring/주석 참고, 여기는 **왜 이렇게 설계했는지**만 정리.

## 왜 3단계로 나눴나
DCC(다변량 상관관계 추정)는 종목 수(N)가 커질수록 계산량이 N² 이상으로 급증한다. 반면 univariate GARCH(종목별 변동성 추정)는 종목끼리 독립적이라 N에 비례(선형)해서만 늘어난다. 그래서:

1. **univariate GARCH는 전체 종목(~3,700개) 대상으로** — 비용이 싸고(선형), 유니버스/필터 조건과 무관하게 재사용 가능한 공용 재료라서 미리 다 계산해둠
2. **필터(02_filter)가 실제 투자 유니버스(N=100)를 추림** — DCC를 돌릴 대상 범위를 좁히는 역할
3. **DCC는 필터로 추려진 N=100짜리에만 적용** — 1단계에서 이미 계산해둔 표준화잔차를 재사용하므로 빠름(수십 초)

이 분리 덕분에 "필터 조건이 바뀌어도 1단계를 다시 돌릴 필요 없음" — 1단계는 유니버스와 무관한 독립적인 재료이기 때문.

## 1단계: univariate GARCH
- 모델은 **GARCH(1,1)** 고정. DCC 논문(Engle 2002) 자체가 1단계로 GARCH(1,1)을 쓰고, 고차 모델을 써도 일별 주가수익률에서는 실증적으로 개선이 거의 없다고 알려져 있음. 지금 단계에서 과도한 엔지니어링.
- **피팅은 전체 히스토리로, 저장은 최근 500거래일(`STORE_WINDOW`)만.** 모델 정확도를 위해 가진 데이터는 다 쓰지만, DCC가 실제로 쓰는 건 1~2년치 윈도우뿐이라 전체(10년치)를 매번 다 저장하면 쓰기 비용만 커짐.
- 최소 500거래일(`MIN_OBS`) 미만인 종목은 피팅 스킵. 최근 상장했거나 데이터 짧은 종목은 애초에 안정적인 GARCH 추정이 안 됨.
- **모수 재추정(주 1회) vs 변동성 갱신(매일) 분리**: omega/alpha/beta는 하루 사이 거의 안 바뀌는데 MLE 재추정(`fit()`)은 비쌈(3,767종목 기준 약 29분, 대부분 DB I/O). 반면 조건부변동성/표준화잔차는 매일 새 수익률이 들어올 때마다 재귀식으로 갱신돼야 "오늘자" 값이 의미 있음. 그래서:
  - `fit_univariate_garch.py` (주 1회, 주말): `arch`의 `model.fit()`으로 모수 전체 재추정 + 그날 cond_vol/std_resid도 저장
  - `update_univariate_garch.py` (매일): 저장된 모수를 `model.fix(params)`에 넣어 **재귀식만** 다시 계산 (최적화 없음, 종목당 약 17배 빠름 — 0.0275초 → 0.0016초). 저장된 모수 없는 티커(신규 등)는 자동으로 `fit()` 폴백.
  - 단, 스크립트 전체 소요시간은 종목별 DB 조회/저장(I/O)이 지배적이라, 연산 자체가 17배 빨라져도 전체 체감 개선은 그보다 작음 (I/O는 그대로라서).

## 2단계: 필터 연동
- `02_filter`가 선정한 유니버스(`universe_selection` 테이블)를 그대로 읽어옴. 03 쪽에서 필터 로직을 알 필요 없음 — 그냥 "티커 목록"만 받는 느슨한 결합(loose coupling).
- 유니버스에는 있는데 1단계에서 GARCH 피팅이 스킵된 티커(히스토리 부족 등)는 **자동으로, 그러나 명시적으로 로그를 남기고** 제외됨 (`fetch_std_resid`가 제외된 티커 리스트를 같이 반환).

## 3단계: DCC
- Engle(2002) 2단계 추정법. 1단계(univariate GARCH)의 표준화잔차를 입력으로 받아 동적상관행렬만 추정.
- **최적화 안정성 이슈와 해결**: 초기엔 `a,b`에 직접 제약(`a+b<1` 등)을 걸고 페널티로 어기면 큰 값을 리턴하는 방식을 썼는데, 이게 목적함수에 불연속적인 "절벽"을 만들어서 최적화가 운에 따라 전혀 다른 결과(지역해)에 수렴하는 문제가 있었음. **재매개화**(제약 있는 `(a,b)`를 제약 없는 `(u,v)`로 변환해서 탐색하고, 계산 시점에만 다시 `(a,b)`로 변환)로 절벽을 없애고, 최적화 알고리즘도 Nelder-Mead(느림, 평가 횟수 많음) → L-BFGS-B(그래디언트 기반, 빠름)로 교체. 서로 다른 시드 2개에서 출발해서 더 나은 쪽을 채택해 지역해 위험을 추가로 낮춤. 결과: 동일 입력에 대해 100% 재현 가능해졌고 속도도 6배 개선(300초대 → 50초대).
- **`(a,b)` 재추정(주 1회) vs Σ 갱신(매일) 분리**: `(a,b)` 최적화가 비싼 부분이고(`Qbar` 계산이나 재귀식 자체는 원래도 쌈). GARCH 1단계와 같은 이유로 똑같이 분리함:
  - `fit_dcc.py` (주 1회, 주말): `(a,b)` 전체 MLE 재추정(`fit_dcc_ab`) + 그날 Σ까지 저장
  - `update_dcc.py` (매일): 저장된 `(a,b)` 재사용, `Qbar`는 **그날그날의 유니버스로 매번 새로 계산**(`apply_dcc`) — 유니버스가 매일 살짝 바뀌어도(02_filter 재랭킹) `Qbar`를 캐시하지 않고 매번 다시 만들기 때문에 차원 불일치 문제가 없음. `(a,b)`라는 두 스칼라만 "상관관계가 충격에 반응하는 정도"로 재사용하는 거라 유니버스 소폭 변화에 안전함. 저장된 `(a,b)` 없으면 자동 `fit_dcc_ab` 폴백.
  - 테스트 결과: 전체 재추정 약 50초 → 캐시 재사용 시 약 9.6초로 단축.

## 라벨(label) 시스템 — 기본값 vs 사용자 커스텀 분리
`universe_selection`, `covariance_matrix` 둘 다 기본키에 `label` 컬럼이 들어있음 (`as_of_date`만으로는 부족).

- 이유: 사용자가 파라미터를 바꿔서 자기만의 필터/DCC를 돌리면, 그 결과가 **같은 날짜의 시스템 기본값을 덮어쓰면 안 됨** — 나이트리 자동 파이프라인이 모르는 사이에 사용자의 일회성 설정으로 바뀌어버리는 사고가 날 수 있음.
- `label='default'`: 나이트리 자동 실행 전용. `fetch_latest_universe()`/`run_dcc.py`를 인자 없이 호출하면 항상 이것만 봄.
- 그 외 라벨: 사용자 커스텀 실행. 같은 날짜에 여러 개 공존 가능, 서로 안 겹침.
- 향후 웹에서 사용자 커스텀 필터/DCC를 지원할 때, 요청마다 고유 라벨(세션ID 등)을 붙여서 이 구조를 그대로 재사용하면 됨.

## DB 스키마 요약
- `garch_estimates(ticker, date, cond_vol, std_resid)` — 1단계 결과, 최근 500일만
- `garch_params(ticker, fit_date, mu, omega, alpha, beta)` — 1단계 모수, 주 1회 갱신 (`update_univariate_garch.py`가 매일 재사용)
- `universe_selection(as_of_date, label, ticker, rank, score)` — 02_filter 결과
- `dcc_params(label, fit_date, a, b, converged, log_likelihood)` — DCC 모수, 주 1회 갱신 (`update_dcc.py`가 매일 재사용)
- `covariance_matrix(as_of_date, label, ticker_i, ticker_j, covariance)` — 최종 Σ, N×N을 long format으로 저장

- ~~02_filter가 느림 (~58초)~~ → 해결됨. `fetch_price_history`의 SQL에 `WHERE date <= :as_of_date`만 있고 하한선이 없어서, 10년치 전체를 다 읽어온 다음 파이썬에서 최근 1.5년치만 필터링하고 있었음 (데이터가 쌓일수록 더 느려지는 구조). SQL의 `WHERE`절에 하한선(`cutoff`)을 추가해서 DB가 필요한 구간만 돌려주게 수정 → 9.8초로 약 6배 개선. 여전히 종목별 파이썬 for문(`compute_raw_factors`)은 남아있어서, 더 빨라져야 하면 다음 최적화 대상.
- **DCC 결과 `b≈0`**: 현재 유니버스(상위 100개)에서 상관관계의 날짜 간 지속성이 거의 없다는 결과가 재현성 있게 나오고 있음. 최적화 버그는 아닌 게 확인됐지만, 이게 진짜 이 유니버스/기간의 데이터 특성인지, 아니면 모델 설정(윈도우 길이 등) 때문인지는 추가 검증 필요.
- **미국 종목 시가총액은 근사치**: 현재 발행주식수(고정값) × 과거 수정종가로 계산 — 자사주매입/유상증자로 인한 실제 발행주식수 변화는 반영 안 됨 (분할은 수정종가 덕분에 정확히 반영됨).
- **02_filter의 52주 고점 근접도(`compute_high_proximity`)는 `close_price`(비조정) 기준**: 모멘텀/샤프비율/MDD는 다 `daily_return`(조정됨)을 쓰는데 이것만 시간에 걸친 가격 비율(최고가 vs 현재가)이라 `close_price`를 씀. 그 기간 중 액면분할한 종목은 왜곡 가능(US는 `adj_close`가 있어서 고칠 수 있지만 KRX는 `adj_close` 자체가 없어서 못 고침). 분할이 드문 이벤트라 지금은 그냥 알고 넘어가기로 함 — 나중에 특정 종목 결과가 이상하면 제일 먼저 의심할 지점.
